Authentication & Accounts

Password and Google identity, JWT issuance, and session verification. Passwords are BCrypt-hashed; tokens carry the user id, role, and host flag and expire after one hour.

Register (email & password)

POST/auth/register
  1. The user types a username, email, and password and presses Create account. That press doesn't fire a click handler — it submits the surrounding form, and submitting the form is what actually runs handleSubmit.client/src/pages/auth/Register.jsx:35-48, 93-143
  2. Rather than talk to the server itself, the page leans on the shared auth context: handleSubmit flips on a loading flag and calls register(), which is the piece that actually POSTs the credentials.client/src/context/AuthContext.jsx:113-122
  3. On the server the request first meets the controller, which stays deliberately thin — it binds the JSON into a DTO and hands the whole thing off to the auth service.server/Controllers/AuthController.cs:24-38
  4. This is where the real work lives: the service makes sure nobody already owns that email, runs the password through BCrypt so the plain text is never stored, builds the new User, and saves it.server/Services/AuthService.cs:25-49
  5. With a user now in the database, a JWT is minted and stamped with their id, role, and host flag, then signed and set to expire an hour later.server/Services/TokenService.cs:18-50
  6. Back in the browser, saveAuth tucks the token and user into localStorage, wires the token onto future requests, and the app quietly redirects home — now signed in.client/src/context/AuthContext.jsx:90-101

Log in (email & password)

POST/auth/login
  1. The user fills in their email and password and clicks Log in, which submits the form and hands control to handleSubmit.client/src/pages/auth/Login.jsx:45-58, 106-142
  2. The handler passes those two values to the context's login(), which POSTs them up to the login endpoint.client/src/context/AuthContext.jsx:103-111
  3. The controller is a thin pass-through again — it simply forwards the request into the auth service and waits.server/Controllers/AuthController.cs:40-54
  4. The service looks the user up by email, then BCrypt-verifies the password against the stored hash; if the user is missing or the password is wrong, it just returns nothing.server/Services/AuthService.cs:51-77
  5. Notice how every kind of failure collapses into the same generic 401 — the message never says whether it was the email or the password that was off, so nobody can fish for which accounts exist. A success mints the JWT.server/Controllers/AuthController.cs:45-51
  6. saveAuth stores the session, and navigateAfterAuth adds a nice touch — if the user was bounced here from a protected page, it sends them back to that ?returnTo path instead of the homepage.client/src/pages/auth/Login.jsx:18-26

Sign in / sign up with Google

POST/auth/google
  1. Before anything can happen the button has to bootstrap itself — it injects Google's script, initializes with your client id, and renders Google's own official button into the page.client/src/components/GoogleSignInButton.jsx:44-107
  2. Once the user picks their Google account, Google hands back a signed credential; that fires handleGoogleCredential, which passes it along to loginWithGoogle.client/src/pages/auth/Login.jsx:28-43
  3. The context POSTs that credential — not a password — up to the Google endpoint.client/src/context/AuthContext.jsx:124-130
  4. The server can't just take Google's word for it, so it validates the token against your client id and insists the email is verified before trusting anything inside it.server/Services/AuthService.cs:79-114
  5. Then comes the find-or-create: if the person already exists (by Google id or email) it links Google onto that account, otherwise it creates a fresh one — either way it ends holding a JWT. That's why signup and login are the same endpoint.server/Services/AuthService.cs:116-158
  6. From here it rejoins the normal path — saveAuth stores the session and the app navigates home.client/src/context/AuthContext.jsx:90-101

Session restore (page reload)

GET/auth/me
  1. When the app first loads it doesn't assume you're anyone — loadCurrentUser peeks into localStorage for a saved token, and if there isn't one it simply settles into a logged-out state.client/src/context/AuthContext.jsx:149-156
  2. If a token is there, it re-attaches it to the axios headers and asks the server "who am I?" by calling /auth/me.client/src/context/AuthContext.jsx:158-163
  3. That request has to clear the JWT middleware, which re-checks the signature, issuer, audience, and that the token hasn't expired.server/Program.cs:52-65
  4. If the token holds up, the controller reads the user id out of it and the service loads a fresh copy from the database — so any profile or host changes made since login show up right away.server/Controllers/AuthController.cs:83-108
  5. A valid response sets the user; a 401 or 403 means the token is dead, so the session gets wiped clean.client/src/context/AuthContext.jsx:164-178
  6. All the while the route guards hold the UI on a "Loading…" state until this resolves, then either let the page through or redirect to login.client/src/components/ProtectedRoute.jsx:4-16

Become a host (entry)

POST/auth/become-host
  1. Clicking Become a host in the header runs handleHosting, which decides where to send you — for someone who isn't a host yet, that's the /become-host route.client/src/components/MarketplaceHeader.jsx:75-87
  2. That route does one thing: render the onboarding wizard.client/src/App.jsx:85-92 · pages/host/HostOnboarding.jsx:1-6
  3. The actual promotion to host happens at the end of that wizard, not here — see Onboarding. (There's a standalone endpoint for it too, but the app doesn't currently take that route.)server/Controllers/AuthController.cs:360-385

User Profile & Host Profiles

Editable profile fields (bio, work, interests, Airbnb-style prompts) plus public and private host-profile aggregates.

Edit my profile

PUT/auth/me/profile

  2. Editing inside the modal doesn't save anything yet — it only updates a draft copy of the form held in state, so nothing is committed until you're ready.client/src/pages/user/ProfilePage.jsx:686-693
  3. When you do commit, handleSubmit takes that whole draft and calls updateMyProfile.client/src/pages/user/ProfilePage.jsx:694-712
  4. The PUT reaches the controller, which passes the payload straight through to the service.server/Controllers/AuthController.cs:111-136
  5. The service tidies everything up — blank fields become null rather than empty strings, and the interests list is flattened into a single stored value — then saves and hands back the refreshed profile.server/Services/AuthService.cs:192-222

My host profile (private)

  1. When you look at your own host profile, the app asks for the private version through getMyHostProfile.client/src/api/api.js:58-61
  2. The controller runs the shared profile builder but tells it to include your unlisted drafts, since this is your own behind-the-scenes view.server/Controllers/AuthController.cs:138-163
  3. That builder is where the numbers come from — it counts your listings, tallies reviews, and averages your rating.server/Controllers/AuthController.cs:181+

Public host profile

GET/auth/hosts/{hostId}/profile
  1. When a guest lands on one of your listings, the page pulls your public host card with getHostProfile(hostId).client/src/pages/properties/PropertyDetails.jsx:464-490
  2. It's the same builder as before, but told to show only your public listings — and because anyone can view it, no login is required.server/Controllers/AuthController.cs:165-179

Full CRUD plus a draft/publish lifecycle. Listings carry structured address + map pin, amenities, house rules, safety, cancellation policy, an availability window, and price. Every write broadcasts a realtime event.

Create listing

POST/properties
  1. A host works through the create wizard, and any photos are uploaded to S3 as they go (that's the Uploads flow next door).client/src/pages/host/ListingWizard.jsx:295-596
  2. Hitting Save listing runs handleSubmit, which packages up the form and calls createListing.client/src/pages/host/ListingWizard.jsx:559-595
  3. The controller first makes sure the caller is genuinely a host, then puts the payload through ValidateFullListing before touching the database.server/Controllers/PropertiesController.cs:134-172
  4. It deliberately creates the property as unlisted but available — a private draft — saves it, and only then attaches the image rows.server/Controllers/PropertiesController.cs:174-181
  5. Finally it fires a realtime property·created event so any open dashboards refresh themselves, and the wizard sends the host over to their listings.server/Controllers/PropertiesController.cs:182-189

Browse public listings

GET/properties
  1. The moment Explore mounts it kicks off loadListings, which reaches for getPublicListings.client/src/pages/properties/Explore.jsx:116-133
  2. The server only sends back listings that are actually bookable — listed, available, and not past their end date — with the newest ones first.server/Controllers/PropertiesController.cs:45-57
  3. To keep it quick it fetches the images and host summaries for the whole batch in a handful of queries rather than one round-trip per listing.server/Controllers/PropertiesController.cs:717-804
  4. The grid renders, and a realtime listener quietly re-fetches whenever a property or booking changes, so the page keeps itself current without a refresh.client/src/pages/properties/Explore.jsx:135-143

Single property page

GET/properties/{id}
  1. Clicking a card routes to /properties/:id, and the page immediately loads just that one property with getProperty(id).client/src/pages/properties/PropertyDetails.jsx:1079-1098
  2. The controller fetches it and maps the images, the host card, and an IsOwner flag tailored to whoever happens to be asking.server/Controllers/PropertiesController.cs:71-89
  3. That IsOwner is worked out inside MapProperty — it's the switch that lets the UI show owner controls to you but hide them from everyone else.server/Controllers/PropertiesController.cs:806-868

Availability & blocked dates

GET/properties/{id}/availability

  2. The server returns the bookable window along with the ranges already blocked by accepted bookings.server/Controllers/PropertiesController.cs:91-132

Update listing

  1. When a host clicks Edit, the app doesn't reuse whatever was on the card — openEditor re-fetches a fresh copy of the listing first, so you're always editing the latest.client/src/pages/hosting/HostingDashboard.jsx:559-567

Publish / unpublish

PATCH/properties/{id}/publish PATCH/…/unpublish

Image Upload (S3)

The browser uploads photos directly to S3 with a short-lived presigned URL; the backend never proxies the file bytes.

Upload property photos

POST/uploads/property-image-url
  1. The host picks one or more image files in the wizard or editor, which triggers handlePhotoChange.client/src/pages/host/ListingWizard.jsx:486-523
  2. For each file, uploadPropertyImage does a little two-step — first it asks the backend for a presigned upload URL.client/src/api/api.js:81-100
  3. The controller passes that request to the S3 service, which checks the file type is one it allows and mints a unique object key for it.server/Controllers/UploadsController.cs:21-56
  4. It hands back a short-lived presigned PUT URL together with the public URL the file will eventually live at.server/Services/S3ImageUploadService.cs:26-66
  5. Now the browser uploads the actual bytes straight to S3 — they never pass through your server, which keeps it lean and fast.client/src/api/api.js:93-97
  6. The returned public URL is appended to the form's photo list, ready to be saved alongside the rest of the listing.client/src/pages/host/ListingWizard.jsx:508-516

Bookings & Trips

Lifecycle Pending → Accepted / Declined → Completed, with payment status Paid / Refunded. Prices are computed server-side; date and capacity rules are enforced on every request.

Request a booking

POST/bookings
  1. The guest picks dates and guest counts, clicks Reserve and pay, and confirms in a modal — that confirmation is what runs handleConfirm.client/src/pages/properties/PropertyDetails.jsx:808-828
  2. It sends the request off with createBookingRequest.client/src/api/api.js:148-151
  3. The server is thorough before it commits to anything: it checks the dates make sense, the listing is open, the party fits, and — most importantly — that nothing overlaps a booking that's already been accepted.server/Controllers/BookingController.cs:32-97
  4. It then works out the price itself from the nightly rate, never trusting whatever number the client sent, and creates the booking as Pending.server/Controllers/BookingController.cs:99-119
  5. Right away it opens a Stripe Checkout session, and if Stripe stumbles it deletes the booking it just created so you're never left with a ghost reservation.server/Controllers/BookingController.cs:121-140
  6. It returns the Stripe URL, and the browser hands the guest over to Stripe to actually pay (picked up in Payments).client/src/pages/properties/PropertyDetails.jsx:819-822

Pay an existing booking

POST/bookings/{id}/create-payment-session
  1. If a booking was created but the guest backed out of paying, they can return to My trips and hit Pay now, which runs handlePayNow.client/src/pages/user/MyTripsPage.jsx:50-72
  2. That spins up a fresh payment session through createBookingPaymentSession.client/src/api/api.js:177-180
  3. The server re-confirms it's really your booking and that it's genuinely still unpaid before it does anything.server/Controllers/BookingController.cs:152-198
  4. It reuses the exact same Checkout builder, stores the new session id, and returns the URL.server/Controllers/BookingController.cs:199-207
  5. And off to Stripe once more.client/src/pages/user/MyTripsPage.jsx:55-60

Host: accept / decline

PUT/bookings/{id}/status
  1. The host opens a request and clicks Accept or Decline, which runs handleStatusChange with the chosen status.client/src/pages/hosting/BookingRequestDetails.jsx:61-91, 167-173
  2. It sends that decision up through updateBookingStatus.client/src/api/api.js:167-170
  3. The server first makes sure it's actually the host acting, then checks the move is even allowed from where the booking currently sits (you can't complete something that's still pending, for instance).server/Controllers/BookingController.cs:278-316
  4. The two rules that really matter live here: you can only accept a booking that's been paid, and declining a paid booking automatically refunds it.server/Controllers/BookingController.cs:318-359
  5. It saves the new status and pings both the guest and the host in realtime, so their screens update the instant the decision lands.server/Controllers/BookingController.cs:361-390

Guest self-checkout

POST/bookings/{id}/checkout
  1. On their booking, the guest taps Checkout, which runs handleCheckout.client/src/pages/trips/BookingDetails.jsx:96-118, 283
  2. That calls checkoutBooking for this particular booking.client/src/api/api.js:172-175
  3. The server marks the stay as checked out — and that quiet status change is exactly what opens up the ability to leave a review.server/Controllers/BookingController.cs:394-450

Read bookings (inbox & trips)

GET/bookings/host/requests GET/bookings/my-trips
  1. The host's dashboard pulls its incoming requests with getBookingRequests, while a traveller's page loads their own trips with getMyTrips.client/src/api/api.js:141-155
  2. One endpoint gathers everything sitting in the host's queue waiting on a decision.server/Controllers/BookingController.cs:454-508
  3. The other returns the guest's own trips, and a single booking has its own detail endpoint on top of those.server/Controllers/BookingController.cs:210-276, 510-560

Payments (Stripe)

Stripe Checkout for card payments in MYR. The signature-verified webhook — not the success redirect — is the source of truth for payment. Idempotency guards protect against Stripe retries.

Create Checkout session

internal
  1. This isn't an endpoint of its own — it's called from inside booking creation, handed the booking id, the title, and the amount.server/Controllers/BookingController.cs:121-129
  2. It assembles a Checkout session set to card payments, with success and cancel URLs that point right back at your app.server/Settings/StripePaymentService.cs:20-36
  3. The single line item uses the amount the server calculated, expressed in sen, and it tucks the booking id into the session metadata so the payment can be traced back to it later.server/Settings/StripePaymentService.cs:37-57
  4. Then it calls Stripe and passes the live session straight back up the chain.server/Settings/StripePaymentService.cs:59-60

Payment webhook (confirmation)

POST/payments/webhook
  1. Once the guest finishes paying, Stripe calls your server directly — no browser, no login — at the webhook.server/Controllers/PaymentsController.cs:30-50
  2. The very first thing it does is verify Stripe's signature against your webhook secret, so a forged "payment succeeded" call gets thrown out before it can do any harm.server/Controllers/PaymentsController.cs:52-64
  3. It only cares about the "checkout completed" event, and uses the session id on it to find the booking it belongs to.server/Controllers/PaymentsController.cs:66-85
  4. Stripe likes to retry webhooks, so there are guards that quietly do nothing if the booking is already paid or already refunded.server/Controllers/PaymentsController.cs:87-102
  5. Only now does it mark the booking Paid, stash the payment reference for any future refund, and notify both parties — and it's this webhook, not the success page, that counts as real proof of payment.server/Controllers/PaymentsController.cs:104-125

Refund on decline

internal
  1. This kicks in the moment a host declines a booking that had already been paid for.server/Controllers/BookingController.cs:344-359
  2. It refunds against the stored payment reference, and an idempotency key makes sure that even if the decline is retried, the guest can't accidentally be refunded twice.server/Settings/StripePaymentService.cs:63-82

Realtime (SignalR)

A single SignalR hub broadcasts change events so dashboards, the explore grid, and chat update live without polling.

Live update pipeline

HUB/hubs/cloudstay
  1. Once you're logged in, the client quietly opens a live SignalR connection to the hub in the background.client/src/components/RealtimeUpdates.jsx:16-50
  2. The server registers that hub and slots each connection into a group keyed to that user, which is what lets it later message one person specifically.server/Program.cs:119
  3. Whenever something changes, a controller calls the notifier — NotifyUsersAsync to reach specific people, or NotifyAllAsync to tell everyone at once.server/Services/RealtimeNotifier.cs:19-43
  4. The client catches that push and re-broadcasts it as a cloudstay:data-changed browser event, which is the cue individual pages listen for to quietly refetch.client/src/components/RealtimeUpdates.jsx:35-60

Two features live entirely in the browser with no backend endpoint — useful to know when tracing why there's no server call.

The one rule that runs through the whole backend: the client is never trusted for anything that matters — booking prices are recomputed server-side, payment is confirmed only by the signature-verified Stripe webhook, review eligibility is re-checked on submit, and every mutating route verifies ownership before it acts.
